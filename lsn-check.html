01 — Where the numbers live

Replica positions

Run this on the primary. It is the only replica with a complete view of every other replica's position — query it from a secondary and you get meaningful values only for the local row.

ColumnWhat it tells you
end_of_log_lsnThe primary's current end of log. Every other number is measured against this.
last_hardened_lsnHow far the secondary has flushed to disk. Primary's end of log minus this is your true data-loss exposure on failover.
last_redone_lsnHow far redo has applied. Behind hardened means redo is lagging — delays failover time, but no data at risk.
truncation_lsnThe point below which log space can be reused. Far behind is what's driving log growth.
log_send_queue_sizeKB of log the primary hasn't shipped yet.
redo_queue_sizeKB received but not yet applied on the secondary.
02 — The rule

What makes a chain unbroken

Each log backup must begin exactly where the previous one ended.

first_lsn == previous last_lsn

Exactly equal, not merely close. A higher first_lsn means log was generated that no backup captured, and recovery cannot cross that point. Nothing in SQL Server flags this for you — neither the DMVs nor msdb warn about gaps, so the check has to be run deliberately.

The database_backup_lsn column is the anchor: it identifies the full backup each log ties back to. When that value changes, someone took a new full backup and started a fresh chain.

03 — The check

Find the gaps

Order by first_lsn, never by backup date. LSN order is the real sequence — timestamps mislead across replicas with clock skew or overlapping jobs.

StatusMeaningWhat to do
OKContiguous with the previous backup.Nothing.
chain startFirst log backup after a full backup.Confirm the full backup exists and is reachable.
GAPA log backup is missing, or was taken on another node and recorded in that node's msdb.Locate the missing file, or take a new full backup to start a fresh chain.
overlapUsually a copy-only or differently-scoped backup mixed in.Normally harmless — confirm what produced it.
04 — The trap

msdb does not replicate

Each node only knows about backups taken on itself. If jobs have moved between replicas — or a failover happened mid-week — the gap check run on one node will report breaks that do not exist.

Run it on every replica, or pull all backupset rows into one table via linked servers and check the merged set. The server_name column shows which node produced each backup, so a chain that hops replicas is visible rather than mysterious.
