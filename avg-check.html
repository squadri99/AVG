AVG_CHECK

Availability group · secondary replica diagnostics

Working out which layer actually failed when log backups stop on a secondary, and proving it before you change anything.

35250 primary not active 3041 backup failed 50000 re-raised 1408 join failed

The endpoint is per instance, not per database. If some databases succeed, connectivity is proven — stop testing it.

01 — Triage

Count before you diagnose

The scope of the failure identifies the layer, and it does so more reliably than any single error message. A mirroring endpoint serves the whole instance — it cannot be selectively broken for four databases out of forty.

Successful backups on other databases are positive evidence that the replica connection is live right now.

Some succeeding → skip the network entirely

This matters because 35250 reads like a connectivity error and sends people to firewalls and endpoints first. A failed telnet from the wrong host, or to a port the AG does not use, then appears to confirm a theory that the evidence already ruled out.

Databases clustered at an old timestamp while the rest are current: that timestamp is your event. Databases absent from the list entirely were never backed up on this node at all.

02 — Instance layer

When every database fails

Only relevant if the whole instance is affected. Work outward from SQL, not inward from the network.

last_connect_error_description is the field that usually names the fault outright. Compare both nodes — if the primary sees the secondary as connected but not the reverse, the problem is one-way routing, not a dead endpoint.

Node-to-node rules are usually scoped to the cluster members, so a test from a workstation or jump box fails by design. Only a test from the replica itself means anything.

If connection_auth_desc shows CERTIFICATE, check expiry — endpoint certificates lapse quietly and take the connection with them. SELECT name, expiry_date FROM sys.certificates;

04 — Confirm

Expectation versus reality

A NULL from one query is a hint, not proof. This compares what the cluster believes should exist on this node against what actually does — an independent confirmation from different metadata.

ResultState
local_db_id NULLThe AG expects the database here and it does not exist. Needs seeding, then joining.
local_state RESTORINGPresent and restored WITH NORECOVERY, never joined. One statement to fix.
local_state ONLINERecovered locally — an independent copy, not a replica. Drop and reseed; do not attempt to join.

Nobody has to remove a database for it to leave an AG on one replica.

A restore silently drops AG membership on that node

Common ways this happens without anyone doing it deliberately: a refresh or point-in-time restore on the secondary that was never re-joined; automatic seeding that failed partway; the secondary rebuilt and databases restored back without membership; or a replica added to the AG after the databases were, so the join never ran for those.

group_database_id is the identifier that stays constant across replicas. database_id is local to each instance — never carry one node's ID to another.

05 — Repair

Join, seed, or reseed

Already present as RESTORING

Re-run the section 03 query afterwards — state should move to SYNCHRONIZING, then SYNCHRONIZED.

Absent — automatic seeding

Seeding pushes a full copy across the network. Schedule it off-hours for large databases.

Absent — manual seeding

Full backup and log backup from the primary, restore both on the secondary WITH NORECOVERY, then join as above. Use this when automatic seeding is unavailable or the network path cannot take the load.

06 — Protect

Before you fix anything

While the replica is broken, no log backups are happening for those databases. The log on the primary keeps growing and the recovery point keeps drifting.

log_reuse_wait_descMeaning
LOG_BACKUPLog is accumulating for want of a backup. Run log backups on the primary now, independent of the AG work.
AVAILABILITY_REPLICAThe unjoined or lagging secondary is blocking truncation. A log backup alone will not release space until the replica is healthy.
NOTHINGLog is free to reuse.

These counters are cumulative since instance start, not a time window — a bad night averages away across weeks of uptime. Under 5 ms is healthy for log writes, above 20 ms is a real problem. For a specific window, snapshot the DMV, wait, and subtract.

07 — Forensics

Finding when it happened

Work from a known timestamp outwards. Searching days of logs blind is slow; searching ten minutes around a confirmed event is quick.

Every AG state change writes new extended events and pushes older ones out.

Copy AlwaysOn_health*.xel aside before you start repairing
08 — Reference

One cause, five error numbers

The shape of a typical unjoined-database failure, from root to what the on-call engineer actually sees.

  1. Database not joined on this replicaAdded on the primary, or dropped out via a restore, and never joined here.
  2. Backup job targets it by nameJob scope such as USER_DATABASES includes databases that are not local AG members.
  3. Error 35250Log backup cannot reach a primary replica for that database, so it cannot negotiate the log chain.
  4. Error 3041Backup operation aborts. A summary only — carries no diagnostic detail of its own.
  5. Message 50000, severity 16Maintenance script catches the failure and re-raises the text, discarding the original error number.
  6. Agent step reports failureThe same event recorded a second time, in a different place.

Only the first line needs fixing. Everything below it resolves on its own once the database is joined.

Verify against your own environment before running in production
